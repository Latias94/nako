# 0030: Define PostgreSQL-Ready SQL Dialect And Migration Policy

## Status

Accepted.

## Context

ADR 0029 made `taru-db` a facade and moved SQLite implementation code behind a
SQLite-owned adapter module. FRA-040 also made `SqliteStore` crate-private, so
server/runtime code now depends on `TaruDatabase` instead of the concrete
SQLite store.

The remaining risk is subtler: schema files, row codecs, SQL strings,
timestamps, pagination, JSON payloads, and test fixtures still encode SQLite
behavior. That is fine inside the SQLite adapter, but it must be an explicit
policy before adding PostgreSQL. Otherwise a PostgreSQL adapter would either
copy SQLite's storage shape blindly or leak PostgreSQL behavior back into
application services.

FRA-050 inventoried the current SQLite assumptions:

- migrations are a single SQLite-owned list of 30 embedded SQL files;
- SQLite runtime policy enables foreign keys, WAL for on-disk databases, a
  busy timeout, and a one-connection in-memory test pool;
- schema files and repository SQL use SQLite timestamp expressions such as
  `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')`;
- repository SQL uses SQLite positional bind parameters (`?1`, `?2`, ...);
- upserts use SQLite `ON CONFLICT` syntax with `excluded` rows;
- pagination currently uses `LIMIT` and `OFFSET`;
- IDs are bound as canonical strings and parsed back into domain ID newtypes;
- booleans are encoded as integer `0`/`1`;
- JSON payload columns use `*_json` text storage plus `serde_json` codecs;
- several cache, staging, ingestion, and playback fields use millisecond epoch
  columns (`*_at_ms`) rather than ISO timestamp strings;
- SQLite workflow commits use SQLx `Sqlite` transactions and helper functions
  in the SQLite adapter;
- job leasing uses transaction-local claim/update behavior and run-token
  fences rather than PostgreSQL row locks.

Taru is still pre-production, so the clean decision is to keep deleting
compatibility shims and make backend-specific behavior explicit instead of
pretending one SQL dialect can serve all databases.

## Decision

### Backend-Owned Migrations

Migration files are backend-owned. There will be no shared SQL migration file
used by both SQLite and PostgreSQL.

- The current `crates/taru-db/migrations/*.sql` tree is SQLite-owned even if it
  is not yet nested under a `sqlite/` directory.
- PostgreSQL must get its own migration tree when added.
- Migration version numbers are backend-local. Version `0030` in SQLite and
  version `0030` in PostgreSQL do not need to contain identical SQL.
- Behavioral equivalence is proven by repository contracts and facade tests,
  not by textual migration parity.
- Backend-specific migration tests remain inside backend adapter modules.

### Database Lifecycle Naming

The lifecycle trait is named `DatabaseLifecycle`, not `TransactionManager`.

`DatabaseLifecycle` owns startup lifecycle behavior such as applying
migrations. It must not grow ad-hoc transaction APIs. Multi-record transactional
behavior belongs in workflow-shaped repository methods, such as scan commits,
metadata refresh commits, artwork ingest commits, job lease commits, or future
explicit unit-of-work contracts.

### Logical Schema Policy

Repository traits and domain records define the logical schema. Backend storage
types are adapter details:

| Concern | SQLite policy | PostgreSQL target | Contract rule |
| --- | --- | --- | --- |
| Domain IDs | Store canonical strings in `TEXT` columns. | Prefer native `uuid` columns for Taru UUID-backed IDs; keep external/principal identifiers as text. | Callers see domain ID newtypes only. |
| External provider keys | Store provider plus provider-key text parts. | Store the same logical parts, with adapter-owned constraints/indexes. | Provider-native identity never becomes a table identity leak. |
| Enums/statuses | Store stable lowercase strings, optionally constrained. | Store stable lowercase strings with `CHECK` constraints first; avoid PostgreSQL enum types until schema churn settles. | Rust parse/format methods are authoritative. |
| JSON payloads | Store serialized JSON in `TEXT` columns. | Use `jsonb` for logical JSON payload columns unless the value is explicitly opaque text. | Repository methods exchange domain structs or strings as defined today; storage type is hidden. |
| Booleans | Store `INTEGER` 0/1 with codec validation. | Use `boolean`. | Invalid stored values are database errors. |
| Unsigned integers | Store as SQLite `INTEGER` with range checks in codecs. | Use `bigint` or narrower signed types only when the domain range fits. | No silent truncation or unchecked casts. |
| Audit timestamps | Many SQLite fields use ISO UTC text generated by SQLite. | Use `timestamptz` or adapter-bound UTC values; do not expose SQL clock syntax to callers. | Domain behavior, ordering, and tests must not depend on a specific database clock function. |
| Millisecond timestamps | Store as `INTEGER` milliseconds where the domain already speaks in milliseconds. | Store as `bigint` milliseconds unless a future domain decision changes the type. | Millisecond fields remain explicit domain facts, not implicit audit timestamps. |

### SQL Dialect Policy

SQL strings are backend-specific. The facade must not contain SQL fragments and
application services must not know placeholder, upsert, lock, JSON, or
timestamp syntax.

- SQLite repository modules may continue to use `?1` bind parameters.
- PostgreSQL repository modules must use PostgreSQL bind parameters and SQLx
  PostgreSQL types.
- Upsert behavior is repository-method behavior, not a shared SQL string.
- Pagination is expressed through `PageRequest`; each backend chooses safe
  `LIMIT/OFFSET` or a future keyset implementation behind the same contract.
- `RETURNING` is an adapter optimization, not a facade requirement.
- Search projection SQL remains backend-specific until the FRA-100 search
  semantics slice defines a deeper search model.

### Job Lease And Locking Policy

`JobLeaseRepository` is the contract for durable worker ownership.

SQLite may keep using transactional conditional update behavior because SQLite
does not provide PostgreSQL-style row locks. PostgreSQL should use row-level
locking semantics such as `FOR UPDATE SKIP LOCKED`, or an atomic update with
`RETURNING`, when implementing claim behavior. Both implementations must pass
the same backend-neutral job lease contract suite.

The contract, not the SQL shape, defines correctness:

- only claimable jobs are claimed;
- run-token fencing protects heartbeat, success, failure, and cancellation;
- cancellation requests are durable;
- expired leases recover only eligible running jobs.

### Row Codec Policy

SQLite row codecs stay in `taru-db::sqlite::codec` and are not shared with
PostgreSQL. PostgreSQL must have its own row-codec layer because native `uuid`,
`jsonb`, `boolean`, and timestamp types should not be forced through SQLite's
string/integer conventions.

Shared conversion logic may move to domain crates only when it is truly
database-independent, such as canonical enum strings or provider/source part
formatting. SQLx row access helpers, range checks for a concrete SQL type, and
database error mapping remain adapter-owned.

### Contract And Fixture Policy

Backend-neutral tests construct `TaruDatabase` and assert repository behavior
through public repository traits. Backend-specific tests may construct adapter
types only when they intentionally verify migration, runtime, rollback,
locking, or dialect details.

When PostgreSQL is added:

- the existing contract suites must run against SQLite and PostgreSQL;
- PostgreSQL tests may be gated by an environment variable such as
  `TARU_TEST_POSTGRES_URL` or by a test-container feature;
- skipped PostgreSQL integration tests must still compile;
- test fixtures must seed data through repositories unless the test explicitly
  targets a backend migration or dialect edge case.

### FRA-060 Proof

FRA-060 should add the smallest PostgreSQL readiness proof that exposes real
dialect pressure without faking a full backend:

1. introduce a reusable backend contract-test harness shape that can register
   SQLite and optional PostgreSQL backends;
2. keep SQLite as the always-on backend;
3. add a PostgreSQL skeleton only if it has a real connection/lifecycle shape
   and at least one non-trivial contract target, preferably job leases;
4. skip PostgreSQL runtime tests when no PostgreSQL URL is configured, but keep
   the code compiling.

A fake PostgreSQL adapter that delegates to SQLite or returns unsupported for
every repository method is not acceptable.

## Consequences

- PostgreSQL can use native database features without changing Taru's domain
  vocabulary or application services.
- The existing SQLite adapter remains honest: SQLite assumptions are allowed
  inside `taru-db::sqlite`, not at the facade boundary.
- Migration parity is behavioral instead of textual, which avoids fragile SQL
  translation work.
- `DatabaseLifecycle` gives startup code a truthful dependency and leaves room
  for a future migrator/lifecycle split if the facade grows.
- Adding PostgreSQL will require test infrastructure, but the first contract
  target is already clear: job leases.

## Alternatives Considered

- Share one SQL migration tree and translate dialect differences with string
  helpers. Rejected because it hides database semantics, weakens migrations,
  and would make PostgreSQL inherit SQLite storage compromises.
- Force PostgreSQL to store every Taru ID, timestamp, boolean, and JSON value
  exactly like SQLite. Rejected because it wastes PostgreSQL strengths and
  still does not remove dialect differences in locking and migrations.
- Introduce an ORM as the portability layer. Rejected for the same reason as
  ADR 0029: Taru needs explicit workflow commits, durable job ownership,
  redaction-sensitive read models, and backend-specific locking.
- Add a compile-only PostgreSQL adapter with no real behavior. Rejected as the
  primary proof because it would make the architecture look portable without
  proving any hard behavior.
