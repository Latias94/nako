## Decision

Selected `http_webhook` as the first real notification provider adapter.

The adapter should be an outbound HTTP webhook sink inside
`nako-notification-bridge`. It is the narrowest useful target because it can be
tested with a local fixture server, needs no platform account, can bridge to
many automation systems, and does not require Nako core or Addon Protocol
changes.

## Boundaries

- Nako core owns event scheduling, sidecar delivery, and redaction-safe attempt
  records.
- The notification bridge sidecar owns webhook target URL, optional shared
  secret/header, outbound provider calls, payload shaping, provider diagnostics,
  and provider-specific retry decisions.
- The first send path should use a fixed redaction-safe JSON summary, not a
  user-defined template language.
- The first adapter should not introduce a sidecar background queue. Retryable
  provider HTTP failures can surface as safe retryable sidecar failures so
  Nako's existing Addon Event retry is reused.
