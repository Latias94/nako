# AFCR-050 Journal — Paging For Large Browse Surfaces

Date: 2026-05-21
Task: AFCR-050
Status: DONE

## Summary

Implemented the first reusable server-backed paging vertical for the Android
client:

- added shared paging helpers in `BrowsePaging.kt`;
- added `LoadMoreSearch`, `LoadMoreRelationshipIndex`, and `LoadMoreFacet`;
- threaded explicit `PageRequest` values through `BrowseDataSource` and
  `ClientBrowseDataSource`;
- added visible Load more footers for Search, relationship indexes, and
  public-backed facets;
- kept existing content visible when a load-more request fails;
- derived next pages only from Public Client API `limit`, `offset`, and
  `returned`.

Also closed an AFCR-040 wiring gap by adding debug/release
`BuildConfig.NAKO_ALLOW_CLEARTEXT_HTTP` so debug builds explicitly allow local
HTTP while release builds keep the production cleartext-deny policy.

## Decisions

- `PageInfo.nextPageRequestOrNull()` treats `returned < limit` as the only
  no-more-page signal available from the current Public Client API. The client
  does not invent totals.
- Search, relationship indexes, and public-backed facets are the AFCR-050
  vertical proof. Home and Library Detail paging are intentionally deferred
  until this shared policy has had product/UI review.
- Load-more failures remain attached to already loaded content through
  `loadMoreFailure` rather than replacing the entire surface with a failure
  card.
