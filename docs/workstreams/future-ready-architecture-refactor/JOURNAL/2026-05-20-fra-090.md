# FRA-090 — Metadata Candidate Graph

Date: 2026-05-20
Status: Complete

## Context

Before this slice, TMDB, Douban, Bangumi, and NFO mapping code produced
`CanonicalMetadata` directly. That worked for the current merge path, but it
made provider-native payload mapping, provider subject mapping, local NFO
authority, Addons, and future Automation Providers all share one shallow
shape. The long-term architecture needs a provider-neutral candidate seam so
raw provider payloads remain audit/debug artifacts, candidate metadata remains
source-neutral evidence, and Canonical Metadata stays the authoritative item
state after merge policy runs.

## Changes

- Added `MetadataCandidateGraph` records in `taru-core`.
- Rewired `taru-metadata` search/fetch DTOs to carry a candidate graph.
- Changed TMDB, Douban, and Bangumi mapping functions to produce
  `MetadataCandidateRecord`.
- Wrapped provider candidate records with a root `MetadataCandidateSubject`.
- Updated refresh merge to project from the fetched graph into
  `CanonicalMetadata`.
- Updated provider mapping acceptance to prefer root candidate subject facts.
- Added `NfoDocument::candidate_graph`, `NfoDocument::metadata()`, and
  `NfoDocument::from_metadata`.
- Removed the parallel `CanonicalMetadata` storage field from `NfoDocument` so
  NFO has one source of truth: the local candidate graph plus explicit
  projection.
- Rewired NFO import to merge the NFO candidate graph projection.
- Added provider and NFO proof tests.

## Follow-up Risks

- Candidate graph persistence is not added yet. Current provider raw-response
  cache remains raw JSON, while candidate graphs are runtime merge/import
  evidence.
- Multi-node provider hierarchy candidates are modeled but not fully produced
  by TMDB season/episode flows yet.
- Addon and Automation Provider candidate proposals should use the same graph
  records in a later slice when their acceptance workflow is deepened.
- Search still needs a semantic projection boundary; continue with FRA-100.
