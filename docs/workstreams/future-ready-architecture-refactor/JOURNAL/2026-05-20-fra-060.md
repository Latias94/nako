# FRA-060 — PostgreSQL Job Lease Readiness Proof

Date: 2026-05-20
Status: Complete.

## Intent

Add the smallest PostgreSQL readiness proof selected by FRA-050 without
pretending Taru has a full PostgreSQL adapter. The proof should expose real
dialect pressure at the hardest current persistence seam: durable job leases.

## Changes

- Reshaped `crates/taru-db/src/contract_tests.rs` into a reusable backend
  contract harness for the job lease contract.
- Kept SQLite as the always-on backend.
- Added ignored PostgreSQL contract tests gated by `TARU_TEST_POSTGRES_URL`.
- Added a test-only `PostgresStore` under `crates/taru-db/src/postgres.rs`.
- Added a PostgreSQL migration proof at
  `crates/taru-db/migrations/postgres/0001_contract_jobs.sql`.
- Scoped the PostgreSQL SQLx feature to `taru-db` dev-dependencies, so
  production `taru-db` still compiles without the PostgreSQL driver.
- The PostgreSQL proof uses native PostgreSQL behavior instead of SQLite
  storage conventions:
  - UUID columns for Taru UUID-backed IDs;
  - `jsonb` for library roots/options fixture storage;
  - `boolean` is not needed for this proof, but the adapter is not forced
    through SQLite integer booleans;
  - `timestamptz` for job and lease timestamps;
  - PostgreSQL `$1` bind syntax;
  - `FOR UPDATE SKIP LOCKED` for lease claim selection;
  - backend-owned row codecs.
- PostgreSQL tests create a private temporary schema per test and drop it after
  the contract finishes. A small process-local mutex serializes the ignored
  PostgreSQL contract tests to avoid fighting over shared setup.

## What This Proves

The proof is deliberately narrow but meaningful:

- PostgreSQL migrations can be backend-owned and separate from SQLite
  migrations.
- The job lease contract is reusable across backends.
- PostgreSQL can implement the same observable `JobLeaseRepository` behavior
  while using PostgreSQL locking semantics.
- Test-only PostgreSQL support can compile without making PostgreSQL a
  production runtime dependency yet.

## What It Does Not Claim

- `TaruDatabase` still selects SQLite only in production/runtime code.
- PostgreSQL does not implement every repository.
- PostgreSQL migrations are only a contract proof, not the final production
  schema.
- PostgreSQL tests are ignored by default and require `TARU_TEST_POSTGRES_URL`
  plus `--run-ignored only` or `--run-ignored all`.

## Recommended Next Slice

FRA-070 can now move to server runtime composition. PostgreSQL production work
should remain a future focused lane unless the user wants to continue the
persistence track immediately. If persistence continues, the next clean slice
would be to split `taru-db` facade/backend adapter crates or add a second
high-value PostgreSQL contract such as event outbox or metadata refresh.
