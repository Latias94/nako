# FRA-070 — Server Runtime Composition

Date: 2026-05-20
Status: Complete.

## Intent

Keep `TaruApp` as the stable application handle while moving real construction
knowledge out of the root app file. This slice should not introduce empty
pass-through modules. The new boundary must concentrate service construction,
runtime resource construction, startup sequencing, and startup worker
registration.

## Changes

- Added `crates/taru-server/src/app/composition.rs`.
- Replaced the inline `TaruAppInner` struct with `TaruAppComposition`.
- Moved runtime resource construction into `TaruRuntimeResources`:
  - process-local `RuntimeSupervisor`;
  - `StorageBackendRegistry`;
  - scan, metadata/NFO/Addons, and webhook semaphores;
  - metadata provider registry.
- Moved app service construction into `TaruAppServices`.
- Kept `TaruApp` responsible for:
  - database connection creation from config;
  - exposing service handles to HTTP/CLI/test callers;
  - exposing startup report and runtime diagnostics.
- Kept startup workflow execution after service construction and before
  optional managed artwork ingest worker startup.
- Removed the old inline construction path rather than preserving it as a
  compatibility helper.

## What This Proves

- `TaruApp` can stay as the public app handle without owning every runtime
  construction detail.
- Runtime resources can be grouped as a real server composition seam, not as a
  set of generic pass-through wrappers.
- Future network tunnel, AI automation, Addon Manager, or job worker loops can
  attach to a composition boundary without further widening `TaruApp`.

## What It Does Not Claim

- This does not yet split server runtimes into separate crates.
- This does not redesign individual app services.
- Admin API read-model hygiene remains FRA-110.
- Local Inference, Metadata Candidate Graph, and Search semantics remain
  separate follow-on tasks.
