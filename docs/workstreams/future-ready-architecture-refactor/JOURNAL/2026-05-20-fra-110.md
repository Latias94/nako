# 2026-05-20 — FRA-110 Admin/API Contract Hygiene

## Task

Audit Admin API read models and Public Client API mappings after the
persistence/runtime/search refactors so DTOs stay explicit, redacted, and
contract owned.

## Findings

The generated Admin API contract already has a good first boundary: it covers
the eight admin-web read-model routes and has tests proving the app-local
contract excludes raw sensitive fields. Public Client OpenAPI and TypeScript
SDK tests also already reject admin and internal surfaces.

The weak point was `JobResponse`. Although the admin job list DTO was already
redacted, `JobResponse` parsed and serialized persisted `input_json`,
`summary_json`, and `error` directly. That made job-returning HTTP routes echo
raw operational payloads for library scan, NFO, metadata, automation, and
managed artwork workflows. Those payloads can contain secret references,
provider prompts, locators, storage URIs, local paths, or implementation
details. This was persistence-shaped DTO leakage, not a stable client
contract.

Managed artwork failure handling also depended on raw job summary/error JSON
for safe failure codes. The clean boundary is to expose the failure code from
the managed artwork ingest read model itself, not from a generic persisted job
summary bag.

## Changes

- Removed raw `input`, `summary`, and `error` fields from `JobResponse`.
- Added explicit `has_input`, `has_summary`, and `has_error` flags to
  `JobResponse`, matching the already-redacted Admin job list style.
- Replaced the old NFO backup-summary preservation test with a redaction test
  proving `JobResponse` does not serialize raw payload, summary, or error
  details.
- Added `failure_code: Option<String>` to `ManagedArtworkIngestSummary` as a
  narrow safe diagnostic field for managed artwork ingest failures.
- Updated HTTP tests for library scan, NFO import/export, metadata refresh,
  metadata maintenance, automation job enqueueing, managed artwork acceptance,
  managed artwork failure, and managed artwork requeue.

## Follow-up

FRA-120 should focus on repository hygiene around generated frontend/SDK
artifacts and ignore rules. If a future admin UI needs job detail inspection,
it should add job-kind-specific safe detail DTOs rather than re-exposing raw
job input/summary/error JSON.
