# FRA-020 Persistence Architecture Deep Dive

Date: 2026-05-20
Status: DONE

## Task

architecture for SQLite plus future PostgreSQL.

Not all large traits are wrong. Some are read-model or workflow-heavy surfaces.
The issue is that all of them converge on the same concrete adapter type and
test setup.

### SQLite-Specific Assumptions

Observed assumptions that must be isolated before PostgreSQL:

- `sqlx::Sqlite`, `SqlitePool`, `SqliteRow`, and
  `sqlx::Transaction<'_, Sqlite>` are imported through the root of `nako-db`.
- Migrations are embedded as SQLite SQL through one `MIGRATIONS` list.
- Timestamps use SQLite expressions such as
  `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')`.
- Job leasing uses transaction-local `SELECT` followed by `UPDATE`; PostgreSQL
  should use row-level locking semantics such as `FOR UPDATE SKIP LOCKED` where
  appropriate.
- JSON is persisted through SQLite-compatible text columns; PostgreSQL may use
  `jsonb` internally while preserving the same domain contract.
- IDs are persisted as strings in SQLite; PostgreSQL may choose UUID columns
  internally if adapters convert at the boundary.
- Tests construct `SqliteStore::connect_in_memory()` directly across many
  crates, which makes SQLite the implicit persistence contract.

### Existing Strong Points

The code already has good foundations:

- Multi-record commits exist for catalog projection, metadata refresh, NFO
  import, library scan source persistence, managed artwork ingest, selected
  artwork publication, job leases, and staging reservations.
- Domain records and repository traits are separate from SQL implementation.
- `nako-server` already moved many root-app forwarding methods to focused app
  services.
- SQLite behavior is well covered by tests.

The next step is therefore not to invent a new persistence philosophy, but to
make the existing one backend-neutral and testable.

## Decision

Adopt ADR 0029:

- Keep domain records and repository contracts in `nako-core` for now.
- Turn `nako-db` into the facade used by server and tests.
- Move SQLite implementation behind a SQLite-owned adapter module or crate.
- Long-term target:
  - `nako-db`: facade, backend selection, database lifecycle, shared contract
    tests/test helpers;
  - `nako-sqlite`: SQLite SQLx implementation;
  - future `nako-postgres`: PostgreSQL SQLx implementation.
- First implementation may use an internal `nako-db::sqlite` split before a
  crate split, but server services should depend on the facade handle rather
  than `SqliteStore`.
- Add backend-neutral persistence contract tests before large code movement.
- Rename or replace `TransactionManager`; it is a database lifecycle/migration
  seam, not a transaction manager.

## Why This Direction

This gives the clean target architecture without creating premature PostgreSQL
production code:

- The facade prevents `nako-server` from hard-coding SQLite.
- Backend adapters keep dialect differences local.
- Contract tests make future PostgreSQL work measurable.
- Existing repository traits can continue to serve domain crates during the
  transition.
- The work can proceed in vertical slices instead of one risky mega-rename.

## Recommended Next Slice

FRA-030 should create the first backend-neutral contract test harness and run it
against the existing SQLite adapter before major module movement.

Suggested proof target:

1. Add a persistence contract-test module for one high-value workflow commit,
   preferably job lease lifecycle or library scan source commit.
2. Define a small async store factory used by contract tests.
3. Run the same contract against SQLite.
4. Keep existing SQLite-specific migration/dialect tests separate.

Recommended first target: `JobRepository` lease contract.

Reason:

- It is critical for background work correctness.
- PostgreSQL implementation will need different SQL locking behavior.
- The desired behavior is backend-neutral and already well tested on SQLite.
- A contract here will immediately expose whether the facade shape is adequate.
