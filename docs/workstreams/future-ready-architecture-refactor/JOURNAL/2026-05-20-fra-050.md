# FRA-050 — PostgreSQL-Ready SQL Dialect And Migration Policy

Date: 2026-05-20
Status: Complete.

## Intent

Make the persistence layer explicit enough that PostgreSQL can be added without
redesigning Taru's repository contracts or leaking SQL dialect details into
server/application code.

This slice is intentionally policy-heavy, but not documentation-only: it also
removes the misleading `TransactionManager` name because that trait only
exposes database startup lifecycle behavior.

## Inventory

FRA-040 already moved persistence implementation under `taru-db::sqlite`.
FRA-050 inventoried what remains SQLite-specific there:

- `crates/taru-db/src` now has only `contract_tests.rs`, `facade.rs`,
  `lib.rs`, `sqlite.rs`, `tests.rs`, and the `sqlite/` implementation tree.
- `crates/taru-db/migrations` currently contains 30 embedded SQLite migration
  files.
- The SQLite adapter/migration tree contains:
  - 176 occurrences of SQLite `strftime(...)` timestamp expressions;
  - 35 SQLite `ON CONFLICT` upsert statements;
  - 882 SQLite positional bind markers (`?1`, `?2`, ...);
  - 92 `LIMIT`/`OFFSET` markers;
  - 190 `*_json` column/code references;
  - 14 direct `serde_json` codec call sites;
  - 14 boolean integer codec references;
  - 283 ID string-bind sites;
  - 158 ID parse helper references;
  - 86 SQLx SQLite transaction/pool-begin references;
  - 60 `SqliteRow` references;
  - 204 millisecond timestamp (`*_at_ms`) references.
- No SQLite repository code currently uses `FOR UPDATE`, `SKIP LOCKED`, or
  `RETURNING`; PostgreSQL can therefore choose those features without matching
  SQLite SQL text.
- SQLite runtime policy remains backend-specific: foreign keys on, WAL for
  on-disk databases, busy timeout, and one in-memory connection.
- Job lease behavior is the highest-value portability pressure point because
  SQLite uses transactional conditional update behavior, while PostgreSQL
  should use row-level locking or atomic update-with-returning semantics.

## Decisions

Accepted ADR 0030:

- migration files are backend-owned; SQLite and PostgreSQL will not share SQL
  migration files;
- migration version numbers are backend-local and behavioral parity is proven
  by repository contracts;
- SQL dialect differences stay behind backend adapters;
- logical schema decisions are expressed at repository/domain boundaries, while
  storage types are adapter details;
- SQLite row codecs stay in `taru-db::sqlite::codec`; PostgreSQL will get its
  own codec layer;
- backend-neutral tests construct `TaruDatabase` and assert behavior through
  repository traits;
- backend-specific tests may construct adapters only for migration/runtime/
  rollback/locking/dialect details;
- FRA-060 should add a real contract-harness/PostgreSQL readiness proof, not a
  fake adapter that delegates to SQLite or returns unsupported everywhere.

## Code Changes

- Renamed the lifecycle trait from `TransactionManager` to
  `DatabaseLifecycle`.
- Moved the trait file from
  `crates/taru-core/src/repository/transaction.rs` to
  `crates/taru-core/src/repository/lifecycle.rs`.
- Updated `taru-db`, `taru-server`, `taru-library`, `taru-metadata`,
  `taru-nfo`, `taru-automation`, `taru-catalog`, and `taru-events` test/service
  imports to use `DatabaseLifecycle`.
- Kept the method name `migrate()` because the method is currently honest; the
  inaccurate part was the trait name.

## Architecture Notes

The important design constraint is not "write generic SQL". It is the opposite:
keep SQL backend-specific and prove repository behavior through shared
contracts.

For PostgreSQL, this means:

- native `uuid`, `jsonb`, `boolean`, and timestamp types are allowed;
- row-codec and SQLx row helpers should not reuse SQLite's string/integer
  conventions;
- job leasing should use PostgreSQL's concurrency features where appropriate;
- migrations should be written for PostgreSQL directly;
- application services should still see only `TaruDatabase` and repository
  traits.

## FRA-060 Handoff

FRA-060 should implement the smallest proof that reveals real PostgreSQL
dialect pressure:

1. introduce a backend contract-test harness shape that can register SQLite and
   optional PostgreSQL backends;
2. keep SQLite as the always-on backend;
3. add PostgreSQL code only if it has a real lifecycle/connection shape and at
   least one meaningful contract target, preferably job leases;
4. gate PostgreSQL runtime tests behind `TARU_TEST_POSTGRES_URL` or equivalent,
   while keeping the code compiling when the variable is absent.
