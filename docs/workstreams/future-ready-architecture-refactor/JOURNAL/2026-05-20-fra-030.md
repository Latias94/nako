# FRA-030 Backend-Neutral Job Lease Contract

Date: 2026-05-20
Status: DONE

## Task

FRA-030: Introduce backend-neutral persistence contract tests and a first
transaction/unit-of-work seam for multi-record workflow commits.

## Implementation

This slice started with the job lease lifecycle because it is a high-value
workflow boundary and PostgreSQL will need different locking SQL while
preserving the same observable behavior.

Changes:

- split `JobLeaseRepository` out of the broader `JobRepository` contract;
- kept ordinary job enqueue/start/succeed/fail/get/list behavior in
  `JobRepository`;
- implemented `JobLeaseRepository` for `SqliteStore`;
- imported `JobLeaseRepository` in server job runtime and job app service where
  durable lease methods are used;
- added `crates/nako-db/src/contract_tests.rs` as the first contract harness;
- removed duplicate SQLite-only job lease lifecycle tests from
  `crates/nako-db/src/tests.rs`.

The new contract tests are generic over repository traits and do not query
SQLite rows directly. SQLite is currently the first adapter under test.

## Contract Coverage

The first contract suite proves:

- filtered lease claim chooses only queued and matching jobs;
- claimed jobs transition to running and record worker ownership;
- heartbeat refreshes a lease only when the run-token fence matches;
- stale run tokens cannot heartbeat, succeed, fail, or cancel;
- success clears the job into a terminal succeeded state;
- queued cancellation is terminal immediately;
- running cancellation is durable and visible on the next heartbeat;
- only the owning lease can acknowledge cancellation;
- expired-lease recovery affects only running leases that match the recovery
  filter.

## Architecture Notes

This is intentionally not a full database facade yet. The goal was to install a
behavioral safety rail before the large `SqliteStore` split in FRA-040.

The important boundary improvement is that application code can now distinguish
ordinary job state from durable worker ownership. That makes future PostgreSQL
locking behavior easier to implement behind the same contract.
