# 2026-05-18 APW-030

Task: implement the first concrete `metadata_write` Addon Side Effect apply
path for Canonical Metadata.

## Summary

APW-030 implemented a bounded synchronous apply slice for `metadata_write`.
Accepted intake records now move through explicit apply outcome state before
they are considered domain writes. The slice keeps `validation_status`
separate from `apply_status`, adds first-class Addon metadata attribution, and
uses existing Taru metadata/catalog seams instead of direct database mutation
from HTTP code.

## Implemented

- Added `AddonSideEffectApplyStatus` and `AddonSideEffectApplyOutcome`.
- Added SQLite migration `0023_addon_side_effect_apply_outcome.sql`.
- Added `MetadataSource::Addon(AddonId)` and SQLite codec support.
- Added safe apply outcome fields to Addon Side Effect response summaries.
- Added a small metadata commit seam for non-provider metadata writes.
- Implemented minimal `metadata_write` payload normalization for title-like
  fields, overview, release date, runtime, tagline, genres, and tags.
- Merged through `MetadataMergePolicy` with Addon source semantics.
- Hydrated catalog/search after apply.
- Preserved response redaction for raw payload, provenance, Source Locators,
  filesystem paths, provider bodies, token hashes, and raw Addon Tokens.

## Tests

- DB tests cover Addon source round-trip and apply outcome persistence.
- HTTP tests cover authorized apply, catalog/search update, idempotent replay,
  rejected intake `skipped` outcome, and invalid payload `failed` outcome.

## Decisions

- Do not write metadata field locks for Addon writes in this slice. Field locks
  express overwrite protection, not provenance. If Taru needs field-level
  Addon provenance later, add a dedicated provenance table rather than
  overloading locks.
- Do not fabricate provider subjects, provider mappings, or raw provider
  responses for Addon writes.
- Reject unknown metadata payload fields instead of ignoring them, so an Addon
  Sidecar cannot believe a broader write succeeded when Taru only applied the
  minimal supported slice.

## Follow-Up

Run APW-060 to review and close or split the lane. Recommended split:

- a dedicated artwork/artifact protected-write lane for APW-040;
- a dedicated subtitle/NFO/Library File Write policy lane for APW-050;
- an optional event/provenance follow-on if addon-applied metadata needs its
