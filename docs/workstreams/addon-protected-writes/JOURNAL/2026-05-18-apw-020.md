# 2026-05-18 APW-020

Task: audit Addon protected-write seams and choose the first concrete apply
target.

## Summary

APW-020 selected Canonical Metadata as the first concrete Addon protected-write
apply target. The metadata path has the strongest existing Taru-owned seams:
`MetadataMergePolicy`, metadata persistence commits, and catalog hydration.

The next slice must not directly treat an accepted intake record as an applied
write. `validation_status = accepted` only means the Addon Token, permission,
library scope, and target were accepted and recorded. APW-030 must add explicit
apply outcome state and Addon metadata source attribution before writing
Canonical Metadata.

## Key Findings

- Addon Side Effect intake currently persists actor, token, permission, concrete
  Media Library, target, idempotency key, provenance JSON, payload JSON,
  validation status, safe error code, and creation time.
- The `addon_side_effects` table has no apply status, applied-at timestamp,
  apply error code, applied item/source summary, or replay behavior after apply.
- `SubmitAddonSideEffectRequest` stores generic JSON payloads and responses
  expose only safe summaries. That redaction boundary is correct and should
  survive APW-030.
- `MetadataMergePolicy` is shared by provider refresh, hierarchy confirmation,
  and NFO import. APW-030 should reuse it rather than implement addon-specific
  field replacement rules in HTTP code.
- `MetadataRepository::commit_metadata_refresh` is provider-shaped because it
  persists provider raw response and provider mapping. Addon writes may need a
  smaller commit adapter or a renamed/generalized commit that does not invent a
  fake provider subject.
- `CatalogRepository::commit_item_projection` already commits graph replacement
  and search projection together. APW-030 should hydrate catalog/search after
  metadata apply.
- `MetadataSource` has `Local`, `Nfo`, `Provider`, and `User`; it has no Addon
  variant. Mapping addon writes to `Provider(Other(addon_id))` would blur the
  domain language and should be avoided.
- `DomainEventKind` has `ItemMetadataRefreshed` but no addon-specific metadata
  apply event. APW-030 should either add a safe event kind or record a clearly
  scoped metadata event payload without raw payload/provenance leakage.
- Artwork has `ImageAsset` and `ArtworkTask`, but Managed Artwork fetch/cache
  and artifact policy are heavier than the first metadata apply slice.
- NFO/VFS already has atomic replace and backup policy, but addon-driven
  Library File Write requires path derivation, sidecar target policy, and
  backup/redaction choices that are too broad for APW-030.

## Decision

Continue with APW-030 as a Canonical Metadata apply slice, with these
preconditions:

- add side-effect apply outcome state separate from validation status;
- add Addon metadata source attribution in core and DB codec/storage;
- normalize a minimal metadata payload into `CanonicalMetadata`;
- merge through `MetadataMergePolicy` using Addon source semantics;
- persist the metadata update through a Taru-owned repository/service seam;
- hydrate catalog/search after apply;
- keep responses redacted and idempotent.

## Next Step

Run APW-030. Split a smaller source-attribution/schema task if the apply outcome
and `MetadataSource::Addon` changes dominate the implementation.
