# 2026-05-25 — AEF-040 Addon Event Delivery Runtime

## Claim

Nako can deliver manifest-declared Addon Event Subscriptions from the durable
event outbox through a host-owned runtime. The runtime records per-addon,
per-event, per-subscription attempts and keeps Addon Event Delivery separate
from webhook delivery.

## Implementation Notes

- Added `AddonEventDeliveryAttemptRecord` and
  `AddonEventDeliveryRepository` to core.
- Added SQLite and PostgreSQL migrations plus repository implementations for
  `addon_event_delivery_attempts`.
- Added Addon Event request/response envelopes and subscription grant
  validation to `nako-addon-protocol` and `nako-addon-client`.
- Added server runtime and admin routes:
  - `GET /admin/v1/events/{event_id}/addon-event-attempts`
  - `POST /admin/v1/events/{event_id}/addon-events/deliver`
- Admin dispatch responses expose a redacted event summary rather than raw
  outbox payload JSON. The sidecar request still receives the event payload.
- Repeated manual dispatch skips addon/event/subscription tuples that already
  have a succeeded attempt. Forced replay should be designed as a separate API.

All commands passed locally.

## Residual Risks

- PostgreSQL contract tests were not run because `NAKO_TEST_POSTGRES_URL` is
  not configured locally.
- Event subscription filter metadata is persisted in routing plans but not yet
  evaluated by the delivery runtime.
- The runtime currently creates attempts on manual admin dispatch. A future
  scheduler/replay loop should consume `next_retry_at` and avoid duplicate
  concurrent dispatch for the same addon/event/subscription tuple.
