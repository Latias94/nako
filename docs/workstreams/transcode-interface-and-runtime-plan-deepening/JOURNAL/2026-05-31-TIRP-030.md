# TIRP-030 - FFmpeg Adapter Interface Ratchet

Date: 2026-05-31

## Summary

Curated `nako-transcode` exports so server HLS/remux orchestration no longer
imports or constructs raw `HlsRequest`, `RemuxRequest`, `FfmpegCommandBuilder`,
`FfmpegArg`, or overwrite policy details.

## Changes

- Added `FfmpegExecutionPlanner`, `HlsExecutionPlanRequest`, and
  `RemuxExecutionPlanRequest` as the public FFmpeg execution planning
  Interface.
- Kept raw FFmpeg command/request/builder/arg details crate-internal and left
  only `RemuxContainer` exported from the low-level `ffmpeg` module.
- Made `TranscodeExecutionRequest` opaque to external callers while retaining
  crate-internal command details for HLS/remux runners.
- Updated server HLS and remux services to store the execution planner and pass
  high-level execution plan requests.

## Validation

- `cargo nextest run -p nako-transcode "ffmpeg_execution_planner_plans" --no-fail-fast`
- `cargo nextest run -p nako-transcode hls --no-fail-fast`
- `cargo nextest run -p nako-transcode remux --no-fail-fast`
- `cargo nextest run -p nako-server hls --no-fail-fast`
- `cargo fmt --all -- --check`
- `git diff --check`

## Notes

The first `nako-server hls` run hit the local command timeout before result
collection. A rerun of the same command with a longer harness timeout passed.
No HDR tone mapping, subtitle burn-in, hardware capability matrix expansion,
HLS lifecycle consolidation, resource admission unification, generated API
contract changes, or direct `nako-transcode` dependency on `nako-playback` was
introduced.
