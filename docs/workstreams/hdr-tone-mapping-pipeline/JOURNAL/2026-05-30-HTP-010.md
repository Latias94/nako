## Findings

- Existing media probe facts already expose the first required HDR planning
  inputs: pixel format, bit depth, color range/space/transfer/primaries, and
  HDR metadata flags.
- Existing client input can drive the first slice through `supports_hdr`.
- Playback already reports `VideoHdrUnsupported` and propagates coarse
  `prefer_hdr` output constraints, but it does not have a dedicated
  **Color Pipeline Requirement**.
- Transcode policy mirrors coarse HDR preference, but there is no deterministic
  tone-mapping strategy or FFmpeg filter plan yet.
- `ACDN-020` is active on the same playback vocabulary files that `HTP-020`
  would need.

## Decision

The first implementation task is playback-only `HTP-020`: add
**Color Pipeline Requirement** vocabulary and typed reasons in `nako-playback`.
The first real media-output behavior comes later as a software-first HLS
HDR-to-SDR tone-map path.

## Blocker

Do not start HDR implementation while `ACDN-020` is active unless the planner
explicitly serializes the shared playback/transcode scopes.
