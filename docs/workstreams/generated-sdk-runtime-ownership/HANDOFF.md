# Generated SDK Runtime Ownership — Handoff

Status: Active
Last updated: 2026-05-21

## Current State

This lane has just opened. The prior SDK lanes are closed:

- `android-generated-public-client-sdk` moved Android DTO and route mirrors to
  an OpenAPI-backed Kotlin/JVM SDK.
- `generated-sdk-forward-compat-tolerance` made generated public string values
  tolerant of unknown future wire values.

The remaining question is runtime ownership: Android still owns execution,
public error parsing, API-version header checks, redaction, transport failure
mapping, and product diagnostics.

The owner has clarified that shared Rust client core / UniFFI complexity can be
pulled forward now if doing so prevents future architecture debt. Treat early
Rust core as a first-class candidate, not as an automatic follow-on.

## Active Task

`SDKRT-010` is ready.

Goal: inventory current SDK/runtime/app responsibilities, freeze the ownership
matrix, and decide whether runtime behavior stays Android-owned, moves into a
narrow Kotlin SDK/runtime seam, or requires an ADR before code.

## Decisions Already Inherited

- ADR 0025: Public Client API OpenAPI v1 is the SDK contract authority.
- ADR 0026: native shells with shared Rust client core are the long-term
  flagship direction.
- ADR 0031: generated client SDK work was sequenced before mobile Rust/UniFFI;
  this may need amendment or supersession after the owner direction.
- Android UI, navigation, Media3, media sessions, token storage, product copy,
  and platform security policy stay app-owned.
- Generated DTO/request code must remain synchronized from `taru-api` if it is
  generator-owned.

## Open Decisions

- Does bearer header injection belong in SDK runtime or the app adapter?
- Does public error-envelope parsing move to generated `ErrorResponse` in the
  SDK runtime?
- Should API-version header checks become runtime-owned by default?
- Should redaction primitives be shared, or should Android keep
  `SafeRequestPreview` as a product diagnostic model?
- Is the runtime hand-written beside generated DTOs, generated by `taru-api`, a
  separate module, or intentionally deferred?
- Does the chosen boundary require a new ADR or an ADR 0031 update?
- If Rust core is pulled forward, is the first Android tracer app-supplied
  transport plus Rust response interpretation, or full Rust-owned networking?
- Should existing `taru-client` be split into an FFI-safe core plus reqwest
  adapter, or should a new mobile-specific core crate be introduced?
- How will Rust-side public wire values preserve unknown additive strings so
  Android does not regress from the Kotlin generated SDK tolerance lane?
- What Gradle/NDK/UniFFI build topology is acceptable for ordinary Android
  builds?

## Blockers

None. Do not implement runtime movement until `SDKRT-010` freezes the boundary.

## Recommended Next Step

Set a Codex goal for `SDKRT-010` only. That task should produce the inventory,
ownership matrix, selected option, and ADR impact, explicitly comparing Kotlin
runtime versus early shared Rust client core. Parallel workers are not useful
before the boundary is frozen.
